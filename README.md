# aimarket

> Minecraft Bedrock（Endstone）服务端插件：**自建经济内核 + 按钮商店**。
> 目标平台 **Endstone 0.11.x**。运行期**只用 Python 标准库**，不引入任何第三方包，
> 不依赖也不适配 umoney / arc_core / EconomyAPI 等任何外部经济插件。

---

## 这是什么

一个把「经济内核 + 按钮商店 + 玩家自选显示 + 公司/股票/央行」做成一体的服务端插件。
经济系统是自建的（复式记账 + TCC 交易事务），商店、显示、公司等模块直接架在这套内核上，
不再依赖任何外部经济插件。

工程上有几条贯穿全项目的底线：

| 设计底线 | 本项目的做法 |
|---|---|
| 资金变动必须原子 | `Database.transaction()` 统一事务边界（`BEGIN IMMEDIATE` + SAVEPOINT），迁移可整体回滚 |
| 交易绝不先斩后奏 | TCC 三阶段：冻结 → 背包副作用 → 按**实际**成交量结算 |
| 物品绝不静默消失 | 归还失败一律进对账流程，背包服务返回「实际入包数量」 |
| 物价不被失败交易污染 | 价格影响只在成交事务内写，失败交易结构上无法影响物价 |
| 玩家看到的价格 == 实扣的价格 | `get_quote()` 单一价格入口，展示/确认/结算共用 |
| 文案缺失绝不白屏 | 缺键回退内置文案，再不济返回键名并记日志 |

## 安装

插件是一个纯 Python 包，**两种装法都行**。

### 方式一：构建 wheel（Endstone 标准做法）

```bash
pip install build        # 或 uv build
python -m build --wheel
# 把 dist/endstone_aimarket-1.4.1-py3-none-any.whl 丢进服务器的 plugins/ 目录，重启
```

### 方式二：直接把包目录放进 plugins/

```
服务器的 plugins/
└── endstone_aimarket/      ← 直接把本仓库里的同名目录复制进去
```

启动服务器即可。首次启动会自动在 `plugins/aimarket/` 下生成：

```
plugins/aimarket/
├── config.json      主配置（缺失的键会自动补全）
├── prices.json      官方指导价表（193 个物品，15 个分类）
├── aimarket.db      SQLite 数据库（WAL 模式）
└── lang/
    └── zh_CN.json   文案（可自行修改）
```

## 你可以在游戏里做什么

- **出售店**：把货物摆上按钮，其他玩家右击买走。支持固定价，也支持挂官方指导价（随行情自动涨跌）。
- **收购店**：先注入一笔预算，玩家把东西卖给你，货进商店、钱从托管账户出。店主随时可追加预算或取回货物。
- **以物易物店**：例如「2 钻石 ⟵ 1 铁锭」，不涉及货币。
- **系统无限店**（OP）：无限库存的官方商店，用于回收/投放货币、稳定物价。
- 左键点自己店的按钮会弹出拆除确认；别人点会被拦下并提示店主是谁。

## 配置要点

`plugins/aimarket/config.json`：

```jsonc
{
  "economy": {
    "initial_balance_minor": 0,   // 新玩家开户赠送，单位是最小单位：100 = 1 金币
    "tax_bps": 500,               // 商店交易税，单位基点：500 = 5%
    "transfer_tax_bps": 0         // 玩家间转账税
  },
  "shop": {
    "max_per_player": 10,         // 每人最多几个店，0 表示不限
  },
  "market": {
    "dynamic": {                  // 供需驱动调价
      "step_amount_minor": 1000000,  // 每累计这么多成交额，价格跳一档
      "step_bps": 100,               // 一档 = 1%
      "max_buy_increase_bps": 5000,  // 买入价最多上浮 50%
      "max_sell_decrease_bps": 3000, // 回收价最多下浮 30%
      "sell_buy_link_ratio_bps": 5000, // 买入价上涨的 50% 联动到回收价
      "recovery_bps_per_hour": 2     // 每小时向基准价回归 0.02%
    },
    "daily": { "enabled": true, "item_count": 3, "min_bps": -1500, "max_bps": 1500 }
  }
}
```

**关于单位**：所有金额都用**整数「最小单位」**存储，`1 金币 = 100 minor`，
以此彻底避开浮点误差在长期记账里的累积。写配置时留意 `_minor` 与 `_bps` 后缀。

## 货币与外部经济

### 货币服主自定义

`config.json → economy`：

```jsonc
"currency_name": "金币",   // 货币名称（如"钻石""铜板"）
"currency_symbol": "金",   // 金额后缀符号（全服展示统一使用）
"minor_per_unit": 100      // 1 显示单位 = 多少最小单位
```

改完 `/shopadmin reload` 生效，余额、商店、拍卖、银行、股市的展示全部跟随。

### 兼容外部经济插件（umoney / arc_core / EconomyAPI…）

插件启动时会按优先级自动探测已安装的外部经济插件：

```jsonc
"external": {
  "enabled": true,                          // false = 强制只用内置货币系统
  "priority": ["umoney", "arc_core", "EconomyAPI"],
  "plugin": "",                             // 强制指定插件名（留空自动探测）
  "unit_minor": 100,                        // 1 外部货币单位 = 多少最小单位
  "methods": {"get": "", "set": ""}         // 通用适配：外部插件的取/存方法名
}
```

- **检测到外部插件** → 接入桥接：首次开户**导入玩家在外部经济里的存量余额**（老玩家的钱不丢），
  此后内部账本为权威，每次资金变动后实时镜像到外部钱包（UMoney 走官方 `api_*`，
  其他插件在 `methods` 里填两个方法名即可零代码接入）；
- **检测不到** → 使用内置货币系统，两种模式的业务代码完全一致，随时切换。

**一致性保证**：待推送的余额与账本在**同一个事务**里落盘（`bridge_pending` 表），
推送失败由定时任务重试；玩家上线时对账——有待推记录则推内部值（杜绝崩溃窗口刷钱），
否则采纳外部值（兼容外部插件的 `/pay` 改动）。复式记账恒等式在两种模式下都成立。

**关于价格**：`prices.json` 里 `buy` 是玩家买入价、`sell` 是回收价，单位是金币。
只写一边时另一边自动按 50% 推导；回收价高于等于买入价时该物品的回收会**自动暂停**，
防止玩家无限套利。

## 设计要点

### 1. 身份与金额

- 账户主键是内部 `account_id`，`xuid` 只作登录凭据 —— **玩家改名不换账户，不会丢钱**。
  旧名字保留在名称历史表里，可溯源。
- 金额一律 `int64` 最小单位，税率与折扣用基点，全项目禁用 `float` 参与金额运算。

### 2. 复式记账

每笔资金变动都会写一条 `ledger_tx` 和若干 `ledger_entries` 分录，
**分录之和恒为 0**，且每条分录都记下变动后的余额，可以独立于主表对账。

铸造与销毁通过「货币发行」系统账户体现，它的负数余额就是累计发行量。
因此 **M0 + 国库 + 商店托管 = 累计发行量** 这条恒等式永远成立（有自检可验证）。

### 3. 交易事务模型：TCC + Saga

一次交易横跨两个世界：数据库（可回滚）和 Minecraft 背包（不可回滚、还可能部分成功）。
所以采用三阶段：

```
Try     [事务] 冻结买家资金与商店库存，落一条 APPLYING 交易 + saga 记录
Mark    [事务] saga 置为 APPLYING —— 必须在触碰背包之前单独提交
背包    [主线程] 真正发放/收取物品，拿回「实际成交数量」
Confirm [事务] 按实际成交量结算：扣款、入账、计税、扣库存、写流水、更新价格
Cancel  [事务] 释放全部冻结，交易置为 CANCELLED
```

由此得到三个保证：

- **部分成交是一等公民**：背包只能装下 7 个就只按 7 个收钱，多冻结的额度原样释放，不制造虚假退款记录；
- **价格不被失败交易污染**：调价只发生在 Confirm 的同一个事务里；
- **崩溃可恢复**：saga 的 `phase` 在触碰背包前就已落盘。
  重启后 `armed` 的交易自动安全取消（那时背包一定没被动过），
  `applying` 的转人工并**保留冻结**，等 OP 用 `/shopadmin resolve` 裁决 ——
  宁可卡住一笔等人处理，也不静默吞钱吞物。

### 4. 背包序列化

Endstone 0.11 的 `endstone.nbt` 没有 `dump()` / `load()`，只能手动重建标签树。
这里用**自带类型标记**的表示法（`@b` `@s` `@i` `@l` `@f` `@d` `@B` `@I`）记录每个数值的真实标签类型，
避免两个经典陷阱：`CompoundTag.to_dict()` 会把 `ByteArrayTag` 变成 bytes 从而静默丢失整份 NBT
（潜影盒取出来是空的），以及按字段名猜类型会把附魔等级、烟花飞行时间写坏成 0。

### 5. 为 AI 留的数据源

`metric_samples` 表按 (时间桶, 粒度, 指标, 维度) 持续采集：

货币供应量 M0、累计发行、国库与托管沉淀、持仓户数、人均/中位余额、基尼系数、
前 10% 持有占比、物价指数 CPI、通胀率、分物品成交量与成交额、价格走势快照。

`analytics/ai_gateway.py` 已经定义好 `AIAdvisor` 抽象接口与 `MarketSnapshot` / `Suggestion` 数据结构，
并提供了一个不依赖任何模型的 `RuleBasedAdvisor`（通胀、贫富差距、货币沉淀、异常交易四类预警）。
将来接模型只需新增一个 `AIAdvisor` 子类并注册，调用方一行都不用改。

## 公司、贷款与股票

这一层是围绕一个想法设计的：**让经济有主体、有信用、有责任边界**。

### 公司：有限责任不是承诺，是结构

公司是一个独立的经济主体（`accounts.kind = 'company'`）。它的特殊性在于——
**数据库层面禁止公司账户出现负余额**：

```sql
balance_minor INTEGER NOT NULL CHECK (balance_minor >= 0 OR kind = 'system')
```

公司不属于 `system`，所以余额永远 ≥ 0。债务无法被"记"到公司账上变成负数，
缺口只能在系统账户核销。再配合两条约束：

- `loans.guarantee_account_id` 上的 CHECK 禁止把别人的账户设为担保；
- 清算与追债的代码路径只接收公司账户 ID，全程不出现股东的个人账户。

于是"公司欠债不牵连股东"不是一句承诺，而是**想动也动不了**。

公司资产（NAV）的口径，股价和破产清算共用同一份：

```
NAV = 公司账户余额 + 名下收购店托管余额
    + Σ 旗下店铺库存 × 官方回收价 + Σ 店铺收到的货 × 官方回收价
    − 未偿本金 − 应计利息
```

估值一律用**官方回收价**（比标价保守，防止虚高被用来操纵股价）；
没有官方定价的物品按 0 计，不虚增。

### 实体店：个人收费，公司免费

个人开实体店要付一笔不可退的牌照费（进国库）；公司开店免费，但营业额税率更高。
两种经营主体各有代价，而不是"公司更划算"。

### 贷款与追债

资金来自**系统增发**（放贷即铸币，还款即回收），所以通胀会被 M0 指标如实反映出来。
利息按小时计提、到期一次还本付息、支持随时部分还款。

违约触发条件是**逾期或欠款超额，任一满足**。个人违约的处置：

```
① take 背包物品 → ② 立刻把"拿到了什么"落库 → ③ 才做变卖与抵债结算
```

**第 ② 步单独提交、先于任何资金动作**，这是关键：背包不可回滚，
所以先把清单持久化下来。之后即使崩溃，物品也躺在 `repossessed_items` 里可以重新结算 ——
不会出现"物品没了、欠款也没减"。没有官方定价的物品**不销毁**，留着日后归还；
变卖所得超出欠款的部分**退还原主**。

触发后进入持续追债：此后只要有物品进背包就会被自动变卖抵债。

> 一个技术限制值得说明：Endstone 0.11.x **没有**能覆盖所有入包途径的事件
> （`InventoryMoveItemEvent` / `InventoryClickEvent` 是 Java Bukkit 的概念，Endstone 从未提供；
> 容器类事件还在 Unreleased 未发布）。唯一可用的是 `PlayerPickupItemEvent`，
> 而合成、开箱、`/give`、交易、漏斗都会漏网。所以这里用的是
> **定时轮询兜底（只扫处于追债状态的玩家）+ 关键事件加速**，两条腿走路。
> 离线玩家不没收（防误判），登录时补扫，利息照常计。

### 股票：系统做市

```
每股真实资产 = 公司净资产 / 流通股
股价 = 每股真实资产 × (1 ± 随机指数)      # 默认 ±5%
再套涨跌停 ±20%
```

这就是"公司有多少真实资产，加减随机指数"的落地形式。

申购时**钱进公司账户**与**流通股增加**必须在同一个事务里：若申购价等于每股净资产，
两者同比例变化，老股东的每股价值分毫不变（代数上必然成立）。
如果拆到两个事务提交，就等于拿老股东的钱补贴新股东。

注意做市模式下报价含随机噪声，申购价通常不等于每股净资产，
因此会有同量级的稀释或增益（±5% 以内）—— 这是做市模式的固有特性。
要完全无稀释就用每股净资产定价发行，代价是价格脱离"市场价"。

分红按持股比例分配，公司必须保留运营金，钱不够就不发；股息税进国库。
公司破产时股东在清偿顺位最后，通常归零，但**个人账户分文不动**。

## 三种募资：投资 / 融资 / 赞助

公司要钱有三条路，区别只在**出资方换到了什么**：

| 方式 | 出资方得到 | 公司付出 | 命令 |
|---|---|---|---|
| **投资** | 股份（参与分红、承担股价波动） | 股权稀释 | `/biz invest <公司> <金额>` |
| **融资** | 债权（到期还本付息，不占股） | 还本付息义务 | `/biz finance <公司> <金额>` |
| **赞助** | 广告位（名下店铺详情页署名） | 一个署名位 | `/biz sponsor <公司> <金额> [天数]` |

**融资刻意复用了贷款系统**：债务的计息、逾期、追偿、清算受偿顺序全都现成，
只是把债权人从系统银行换成了玩家。加两列（`lender_account_id` / `lender_kind`）就够了，
不必把整套债务逻辑重写一遍。

**清偿顺序里投资者排在银行之前** —— 银行的钱是增发出来的，承受坏账的能力最强；
玩家的钱是真金白银，优先保护：

```
有担保债权 → 投资者债权（融资） → 银行债权 → 最后才是股东
```

### 四道防滥用闸门（全部可配置，设 0 即关闭）

```
fundraising.per_funder_limit_minor   同一玩家对同一公司的累计出资上限
fundraising.cooldown_hours           两次「投资」之间的间隔
fundraising.nav_multiplier_bps       累计募资 ≤ 公司自有资产 × 倍数
fundraising.lock_days                募资到账后禁止分红的锁定期
```

有两处是踩过坑才定下来的：

**冷却只卡投资，不卡融资和赞助。** 投资会推高公司现金从而推高 NAV，而额度挂在 NAV 上，
于是形成「投资 → NAV 上升 → 额度上升 → 再投资」的反馈回路；融资则不同——
现金与负债同步增加，NAV 分毫不变。如果对所有方式都冷却，正常的一次融资加一次赞助
会被硬拖一整天，很难用。

**上限的基数是「自有资产 = NAV − 已募资金」，不是 NAV。** 若直接用 NAV 当基数，
公司募到的钱会立刻抬高自己的基数：1000 → 可募 1000 → NAV 变成 2000 → 可募 2000 → ……
指数膨胀。扣掉已募部分后，上限锁死在最初的自由资产上，**募资无法自抬门槛**。

锁定期则卡在**分红**上：否则公司可以刚募到钱就立刻分给持股最多的发起人，「防募完就跑」就落空了。

## 股票市场

`/stock` 直接打开股市面板，也可以走命令：

- **行情列表**：每家公司一行，带涨跌幅与迷你走势图（`▁▂▃▄▅▆▇█` 八级高度）
- **个股详情**：现价、涨跌幅、走势、净资产、每股净资产、流通股、总市值、股东数、
  资产构成（现金＋库存−负债）、上次分红、大股东名单
- **买入 / 卖出**：面板内直接下单，会自动算出「余额够买几股」「公司现金够回购几股」
- **我的持仓**：市值、成本、盈亏、盈亏率
- **股东名单**：每位股东的持股数与占比

价格是这样算出来的：

```
每股真实资产 = 公司净资产 ÷ 流通股
股价 = 每股真实资产 × (1 ± 随机指数)      # 默认 ±5%
再套涨跌停 ±20%
```

也就是说，**你公司赚了钱、囤了货，股价就会涨**。所有运算都是整数 + 基点，不引入浮点误差。

涨跌颜色遵循中国市场习惯：**涨红、跌绿**。

## 已知边界

- 只面向 Endstone 0.11.x，不保留 0.10 的兼容分支。
- 不导入任何 ARC 旧数据库，是全新的表结构。
- 玩家间市场（玩家挂单撮合）不在本版本范围内，当前只有「店主 ↔ 系统/玩家」的商店模型；
  股票的二级交易也是系统做市而非订单簿。

  因此清算本身会带来一次货币投放，这是设计取舍而非疏漏。

## 中央银行

**央行 = 发行 + 信贷 + 财政，三家合一，一家直营。** 不设独立商业银行，玩家也不得开设
（公司注册时会拦掉含"银行/央行/钱庄/bank"的名称）。

### 行长怎么设置

```jsonc
"bank": {
  "enabled": true,
  "governor_names": ["你的游戏名"],   // ← 在这里填你自己
  "allow_op_fallback": true          // 名单为空时，OP 可临时代理
}
```

首次识别后**自动绑定 XUID**，所以你以后改名也不丢权限，离线同样不影响判定。
没填名字时 `/bank report` 会提示你去填。

### 为什么"能印钞"和"税收归央行"是一件事

```
印钞（放贷 / 公开市场买入） → 货币进入市面 → 通胀压力 ↑
收税（财政收回） / 卖物资   → 货币退出市面 → 通胀压力 ↓
央行账上轧出来的净值 = 市面上流通的钱
```

所以税收在这里不只是财政收入，**它是最直接的抗通胀工具**。

账本上落在三个科目，但在 `/bank report` 里合并成**一张资产负债表**：

| 科目 | 账户 | 干什么 |
|---|---|---|
| 发行 | `sys:mint`（可为负） | 印钞、放贷、公开市场买入 |
| 财政 | `sys:treasury` | 税收、回收货币 |
| 储备 | `bank_reserves` | 公开市场操作吞吐的实物 |

> **为什么不把两个账户物理合并？** 账本里每条分录都存着当时的余额快照，
> 搬钱会让所有历史快照对不上、审计立刻报警。语义合并达到同样效果，且零风险。

### 货币口径

| 指标 | 口径 |
|---|---|
| 基础货币 | 央行累计净投放（`−balance(sys:mint)`） |
| M0 | 玩家 + 公司手上的现金 |
| M1 | M0 + 活期存款 |
| M2 | M1 + 定期 + 理财 |
| 货币乘数 | M1 / M0 |

恒等式：`M0 + 商店托管 + 财政余额 + 各类存款 = 基础货币`，任何时刻都成立。

**关于"货币乘数"要如实说明**：只有央行一家时，没有商业银行的派生货币，乘数会贴近 1。
但只要玩家把钱**存回央行**、央行再放贷出去，乘数依然成立：

```
放贷 A → 玩家收款 → 存回央行 A → 央行可再放贷 A×(1−准备金率) → …
```

所以准备金率是一个**真实生效的刹车**，被约束的对象是央行自己：
`可放贷上限 = 存款总额 × (1 − 准备金率) + 央行自有资产`。

### 玩家业务

| 业务 | 规则 |
|---|---|
| **活期存款** | 随时存取，按整小时单利计息，利率 = 基准 + 活期利差 |
| **定期存款** | 锁定 N 天；到期自动转活期并通知；提前支取按活期利率折算 + 违约金 |
| **透支** | 见下方说明 |
| **信用卡** | 独立卡片，有账单周期与**免息期**、最低还款额、逾期罚息 |
| **按揭** | 以名下实体店作抵押，店铺估值 = 托管资金 + 库存按官方回收价；等额本金分期；违约收走店铺 |
| **理财** | 已落端口（申购 / 赎回 / 到期结算全可用），收益由策略决定。内置固定收益策略，**后续接 AI 时注册一个 `WealthStrategy` 实现即可，界面与数据表都不用改** |

### 透支为什么要绕一圈

数据库有一条硬约束：**玩家账户余额永远不能为负**（`CHECK (balance_minor >= 0 OR kind='system')`）。
所以透支不是"把余额改成负数"，而是 **「授信额度 + 自动放款」**：

```
付款时余额不足 → 缺口 ≤ 剩余额度 → 自动放一笔款补足 → 再付款
```

玩家感受到的是"能花超"，物理上账户余额恒为正，**完全不触碰那条约束**。

### 信贷一律复用贷款系统

透支 / 信用卡 / 按揭 / 再贴现**都在 `loans` 表里有记录**（靠 `product` 区分），
于是计息、逾期判定、追债（没收背包 + 变卖）、坏账核销、清算受偿全部现成，
产品特有的元数据（额度、账单、抵押物）放在各自的表里，通过 `loan_id` 指回来。

**余额一律从 `loans` 派生**，不做冗余字段 —— 天然不会出现"元数据与实际债务不同步"。

### 货币政策工具

| 工具 | 生效方式 |
|---|---|
| **基准利率** | 一个锚，存/贷/透支/信用卡/再贴现利率全部由它加利差派生 |
| **存款准备金率** | 放贷前校验 + 每小时重算放贷上限 |
| **再贴现窗口** | 以实体店抵押的短期周转融资，利率 = 基准 + 加价，抵押率 60% |
| **公开市场操作** | 央行买卖实物储备。买入 = 印钞投放，卖出 = 回收销毁。单次 ≤ M0 × 1% |
| **量化宽松 / 紧缩** | 大额版，单次 ≤ M0 × 2%、冷却 6 小时、`confirm` 二次确认、总额封顶 M0 × 20% |
| **通胀目标 + 自动调节** | 简化泰勒规则，见下 |
| **汇率干预（金对实物购买力）** | 复用 `cpi_bps` 作币值指数。它与公开市场操作是同一次操作的两个视角 |

**自动调节规则**（每小时一次）：

```
偏离 = 通胀率 − 目标通胀率
|偏离| ≤ 容忍带        → 不动（死区）
调整步长 = clamp(偏离/10, −单次上限, +单次上限)
基准利率 = clamp(基准 + 步长, 0, 3%/天)
未到冷却时间          → 跳过
被行长锁定的项        → 跳过
```

三重防震荡：**死区 + 步长上限 + 冷却时间**。行长可以把任意一项**锁定为手动**，
锁定的项自动调节会跳过 —— 这就是"自动 + 行长可覆盖"。

### 金融监管

央行能印钞，所以它**不会因挤兑而破产** —— 挤兑的代价是**超发导致的通胀**。
因此监管盯的是"货币纪律"而不是"偿付能力"：

- **挤兑指数** = 短期净取款 / 存款总额（阈值可配，默认 20%）
- **超发率** = 基础货币增速。它**不依赖滞后的 CPI** —— 挤兑刚发生时物价还没动，
  但基础货币已经跳了
- **资产覆盖率** = 资产 / (存款 + 财政)。含义是"央行用自有资产覆盖了多少对外负债"
  - 100% 表示完全覆盖；低于 100% 说明差额靠发行信用支撑（这是常态）
  - ⚠ 这里**刻意不用传统的"资本充足率"**：央行直营存款 + 能印钞的模型下，
    初始投放的货币天然没有资产支撑，用传统口径会让任何正常放贷都显示成
    "天量资不抵债"，指标就彻底没有信息量了
- **坏账核销**：缺口直接减少央行资产。核销**不需要账本分录** —— 债权不在账本上
  （loans 表单独记），而当初印出去的货币早就在市面上流通了

越线会**主动私聊在线行长**并落库 `bank_alerts`（6 小时内同类只记一次，避免刷屏）。

### 实测对账（公开市场操作）

```
买入 10 个钻石：投放 9,500 金 == 储备增加 9,500 金 == 基础货币增加 9,500 金
卖出  5 个钻石：回收 5,250 金 == 基础货币减少 5,250 金
剩余储备：5 个，账面 4,750 金
```

每一笔货币投放/回收都能与储备变化对上账。
